# 软件测试与质量保证：课程个人复习总复盘

这份文档是我针对本课程项目的**终极学习与复习指南**。它不用于外部展示，而是为了让我自己能用最通俗易懂的语言，彻底搞懂我到底在这个电商平台（Shopizer）里做了些什么，为什么要这么做。

---

## 知识框架全景图

整个项目我实际上完成了软件测试领域里最重要的五个层面的工作，从外到内，从手工到自动化：

1. **黑盒测试 (Black-box)**：不看代码，只把系统当黑盒，根据需求玩数字游戏（找价格边界）。
2. **状态机建模 (FSM)**：把复杂的业务流程画成严谨的数学状态流转图，解决“什么时候该干什么”的问题。
3. **白盒测试 (White-box/Coverage)**：钻进代码内部，一行行测真实运行的代码，用覆盖率数据说话。
4. **自动化流水线 (CI/CD)**：把所有的代码测试全部扔给云端，机器人帮我7x24小时自动运行。
5. **代码可测试性设计与 Mocking 技术**：**（最硬核部分！）** 改造不可测试的垃圾代码，用假替身（Mock/Stub）骗过系统，实现瞬间测试。

## 第一层：黑盒测试 —— 怎么科学地“找茬”？

**复习参考**：`test-reports/PRODUCT_PRICE_TEST_REPORT_ZH.md`

我们日常说的“测出个bug”，在软件工程里不能靠瞎点。在这个部分，我测试的是电商最核心的数据：**产品价格**。

*   **等价类划分**：既然价格有无数种，我就把它分成 7 篮子。
    *   有效篮子：0元促销、正常价、高价、奢侈价。
    *   无效篮子：负数价格、小数位数超过2位（比如 29.999）、完全没填（Null）。
*   **边界值分析**：bug最喜欢藏在边界上。
    *   我测试了 `0.00` (合法边缘)、`-0.01` (非法边缘)、`999.99` 和 `1000.00`（区间转换）。
*   **我发现了什么？** Shopizer 的代码在 Service 层居然没有拦截负数价格！我提议必须加上 `@Min(0)` 注解，否则可能会让老板破产。

## 第二层：功能建模 —— 怎么用 FSM 管控混乱的流程？

**复习参考**：`test-reports/Assignment2_PRODUCT_LISTING_FSM_DESIGN.md`

电商上架商品不是一句话的事，它有草稿、审核、上架、修改、下架......一不小心就会出现“商品还没审核，用户就能买”的灾难。

*   **什么是 有限状态机(FSM)？**
    *   **状态 (State)**：商品当前处在什么阶段（上架了？还是被拒绝了？）。我设计了 7 个状态（如 `DRAFT`, `ACTIVE`）。
    *   **事件 (Event)**：触发改变的动作（如商家点击“提交审批” `submitForApproval`）。
    *   **守卫条件 (Guard)**：**这是重点！** 这是从一个状态走到另一个状态必须满足的前提。
*   **我和第一层的结合**：当商品从“草稿 `DRAFT`” 走向 “待审核 `PENDING`” 时，**守卫条件**发挥作用了：它必须检查商品价格是不是 >= 0，有没有超过 2 位小数。如果价格验证失败，死活不让你走到下一个状态。
*   **复习体会**：FSM 不是写代码，它是画“规则锁”。只有满足特定规则，流程才能继续。这为后面的白盒测试提供了非常严密的逻辑大纲。

## 第三层：打开白盒 —— 追着代码覆盖率 (Code Coverage) 打！

**复习参考**：`Code_Coverage_Report.md`

之前是黑盒，现在我要看看代码到底跑没跑过！我通过 JaCoCo 这个工具，生成了代码覆盖率报告。

*   **我提升了 `ProductPrice Service`（价格服务）**
    *   **现象**：发现源码里 `findByProductSku()`（通过SKU拿价格）和 `saveOrUpdate()`（保存更新）这俩核心方法根本没人测，代码行覆盖率只有可怜的 **42.9%**。
    *   **我干了啥**：写了一个真正的“进数据库、查SKU、改价格数值、存回数据库”的测试，成功把覆盖率拉到了 **57.1%**。
*   **我提升了 `ShoppingCart Service`（购物车服务）**
    *   **现象**：原本只有 **36.3%** 的覆盖率。由于购物车异常情况极其复杂（比如你还没登录时加了购物车，登录后要合并起来；或者购物车里的东西被人删除了）。
    *   **我干了啥**：专门写了 4 个刁钻的测试用例来“激活”这些角落里的代码。最后暴力拉升了 52 行代码覆盖率，干到了 **62.2%**！
*   **复习体会**：看覆盖率就像扫雷，没绿的地方就是地雷可能藏的地方，逼着我写测试去踩那些没踩过的坑。

## 第四层：CI/CD —— 让 GitHub Actions 给我当牛做马

**复习参考**：`CI_WORKFLOW_EXPLAINED_ZH.md`

如果我们每次修改代码，都要自己手动跑一遍上面的所有测试，不仅累，还容易忘。

*   **我在干嘛？** 我写了一个 `.github/workflows/ci.yml` 脚本。相当于给 GitHub 下指令：只要有人推代码过来，你马上租一台云服务器（Ubuntu），装上 Java 17，然后执行所有的单元测试代码（如 `DataUtilsTest`）。
*   **我踩的坑**：
    *   云服务器跑一半不干了，说找不到依赖包。这是因为 Maven 傻乎乎跑去远程仓库找，我教它加了 `-am` 参数，让它先乖乖编译本地的文件。
    *   它又报错说“找不到测试”。原来有些模块压根没写测试代码（真坑）。我教它加了 `-DfailIfNoTests=false`，意思是找不到测试就算了别报错中断。
*   **复习体会**：这就是传说中的 DevOps。写完代码一推，只要网页上亮绿灯 (✅)，就说明我的修改没有把系统搞崩，这就是自动化测试的安全网！

## 第五层：终极硬核 —— 可测试性重构与 Mocking 技术详解

**复习参考**：`test-reports/TESTABLE_DESIGN_AND_MOCKING_EN.md`

这是最难理解、但技术含量最高的一层！为什么需要这一层？因为**世界上有很多代码写得很烂，或者耦合了外接设备（数据库、发邮件），导致它根本没法单独测试！**

### 1. 傻瓜式理解：什么是 Testable Design（可测试设计）和它的反面教程（Bad Design）？

*   **反面教材（烂代码长什么样？）**
    *   我们有个类叫 `IntegrationModulesLoader`。原作者在方法里写死了 `new ObjectMapper()` 去解析 JSON，又写死了直接去硬盘目录读文件（`this.getClassLoader().getResourceAsStream(...)`）。
    *   **为什么烂？** 试想一下，如果我想测试“当 JSON 解析抛出异常时代码怎么处理”，我必须要在代码上做一个真的错误文件。如果它部署在 CI 云服务器上，文件路径不对，测试直接爆栈。这就是——**强耦合、隐藏依赖。它把逻辑和读文件死死绑在了一起。**
*   **我是怎么重构（脱胎换骨）的？**
    *   运用了 **控制反转 (IoC)** 和 **依赖注入 (DI)**。
    *   我不让这个类自己去新建解析器和文件流了。我制定了两个接口标准：`IntegrationModuleSource` (负责不管从哪弄来文本) 和 `IntegrationModuleParser` (负责把文本变成对象)。
    *   我强制要求，在新建这个 Loader 类的适合，调用的人必须把这俩组件作为参数**传给我（注入进来）**。
    *   **怎么测试？** 现在我可以写一个针对测试的“假源 (StubIntegrationModuleSource)”。测试用例里，我给它塞一段手写的死 JSON 字符串进去。立刻就能跑！这叫隔离！

### 2. 傻瓜式理解：什么是 Mock 和 Stub？它们有什么区别？

这是重点中的重点！

*   **【武器 A】什么是 Stub（桩对象/打掩护的）？**
    *   **大白话**：Stub 就是一个没有灵魂的回答机器。你要什么，我死死地返回什么。
    *   **我做的事情**：`DataUtilsTest` 里的测试。源码要计算重量单位的转化，这个方法需要收一个庞大的 `MerchantStore`（商铺）对象。如果创建真正的对象，还得配好数据库，非常沉重。
    *   **我的破解**：我用 Mockito 创建了一个假的 store (`mock(MerchantStore.class)`)。然后我下命令：`when(store.getWeightunitcode()).thenReturn("LB")`。
    *   **作用**：这段代码的意思是：“一旦系统问这个假店铺你的重量代码是啥，你就傻傻地回答 'LB' (磅)。别管别的。” 这样，核心代码就能拿这个 "LB" 顺畅地往下走，去做它的数学计算了。
*   **【武器 B】什么是 Mock（模拟对象/查岗的）？**
    *   **大白话**：Mock 也是个假对象，但它是有脑子的“间谍”。我不只关心返回值，**我更关心我的业务代码有没有认真调用你！用什么参数调用你！**
    *   **我做的事情**：系统里有个 `EmailService` 专门负责发真邮件。
        *   **如果直接测**：我只要一跑测试，我的私人邮箱马上就会收到几百封垃圾邮件，而且发邮件要等网络，极其缓慢。
        *   **我的破解**：我用 `@Mock EmailService mockEmailService` 做了一个假的假邮件服务。
    *   **怎么验证 (Verify)**：假邮件服务根本不知道怎么联网，但只要业务代码下达了“给我发确认邮件”的指令，这个假服务的小本本上就会记录。这个时候：
        1.  **查调用次数**：我用 `verify(mockEmailService, times(1)).sendHtmlEmail(...)` 查岗——系统是不是准确地只让你发了 1 封信？
        2.  **抓捕核心参数 (ArgumentCaptor)**：我像黑客一样拦截了发出去的邮件，验证它的 `subject` 里是不是包含正确的“订单号”，`body` 里是不是包含正确的“金额”。
        3.  **灾难演习**：我更牛的是，我用 `doThrow(new ServiceException(...))` 强行让这个假服务报错（模拟 SMTP 宕机）。然后去观测商城系统是不是能稳定捕获异常，而不是死机。这就叫高级 Mock 测试能力。

### 总结：Mock 与 Stub 的最大区别
*   **Stub：是被动配合的打工人。** 它的任务是为了应付主代码的条件，提供所需的数据，好让主代码顺利执行下去，不报错。我们最后**不会**去检查 Stub 被调用了没有。
*   **Mock：是主动考核的监考官。** 它的重点是为了观察主代码的“行为”。我们最后一定要去 `verify()` 这个 Mock 到底有没有被传唤，传给它的数据到底是对还是错。
