## 一、现场代码演示步骤 (Demo Flow)

**目标**：向大家展示你的代码是活的，测试能成功运行，没有红叉。

**演示操作**：
1. 打开终端 (Terminal)，确保当前目录是项目的根目录 (`shopizerForTest`)。
2. 复制并按下回车运行以下命令。

```bash
./mvnw test -Dtest=ProductPricePartitionTest,EmailServiceMockTest -pl sm-core -Djacoco.skip=true
```
*(注意：这个命令加了 `-Djacoco.skip=true`，它跳过了冗长、烦人的覆盖率警告，直接显示最干净清爽的 `Builders Success` 和 `Failures: 0`)*

   > “现在我刚刚按回车运行了核心模块 `sm-core` 中的重点单元测试。这其中包含了针对产品系统设计的**基于等价类的价格分区侧试**，以及我通过底层重构独立出来的 **EmailService 的 Mock 测试**。正如大家所见，测试运行极快，而且结果显示绿色的 `BUILD SUCCESS`，没有任何一条 Failure。这证明我重构后的代码逻辑和测试套件在当前项目里是极其稳健的。”

## 二、核心必考题解答指南 (Q&A Guide)

如果你在汇报时被问到具体的某个技术细节，请直接参考以下的**“傻瓜式”满分答案**。

### ❓ 问题 1：你的等价类测算分成了几类？
**你的回答**：
“我把系统的核心——**产品价格**的测试，分成了 **7 大分区 (Classes)**。”
1. **零价格**（0.00，用来验证系统的促销品/赠品逻辑是否合法）
2. **正常价格**（0.01 - 999.99，这是测试日常消费品的基础范围）
3. **高价格**（1000 - 9999.99，测试高端电子产品的定价档）
4. **高档价格**（≥ 10000，奢侈品/家具等大额度系统承载能力）
5. **负价格**（< 0，无效输入，故意测试系统的拦截和拒绝机制）
6. **无效的货币精度**（比如 29.999 这种三家小数，测试系统对四舍五入或精度超限的抛错）
7. **空值**（Null，纯粹测试接口缺失价格数据时的空指针容错能力）

### ❓ 问题 2：你的有限状态机 (FSM) 里面有哪几种 State (状态)？
**你的回答**：
“我的商品上架生命周期模型，一共包含了 **7 种严格卡控的状态**。”
1. `DRAFT` (草稿，商家在后台瞎编，别人看不见)
2. `PENDING` (待审核，商家提交后表单被锁定，等待管理员审批这个商品合法性)
3. `ACTIVE` (已上架，这时候前端商城才能正常展示和购买它)
4. `MODIFIED` (已修改，一旦上架后商家又偷偷改了价格或库存，商品必须重新进入这个审核状态，防止乱标价)
5. `REJECTED` (已拒绝，上面那个审核发现价格不对、图不对，直接打回重做)
6. `INACTIVE` (已下架，东西卖完了或者换季不卖了，商家主动撤退)
7. `ARCHIVED` (已归档，相当于软删除作废，留作历史数据查账)

### ❓ 问题 4：（重点）看一下白盒测试的源码？看你随便说说走了哪些函数、哪些分支？

*(这个时候你可以把 IDE 代码切过去，指着说。或者直接按下面这个背)*

**你的回答**：
“在进行白盒代码覆盖率提升时，我专门挑了系统里难度最大、分支极其复杂的 **`ShoppingCartService` (购物车服务)** 代码去攻坚。我给大家举一个走了最复杂分支计算的例子：”

**讲解重点函数 `mergeShoppingCarts()` 分支逻辑：**
> “看，系统里有个 `mergeShoppingCarts()` 函数非常致命。它的实际业务场景是：一个没有登录网站的游客，在网页买了一堆东西放进车里（这是个虚车），然后他觉得不错，准备结账时**登录了自己的账户**（这有个实车）。在这个瞬间，系统必须把两个车里的产品合并。”

> “这个函数里有一堆判断。在测试的时候，我故意写了一个‘刁钻’的单元测试，触发了它里面最隐蔽的 **If-Else 比较分支**：
> 我让游客车里装了 `商品A`，并且我偷偷让这个用户的原生车里**也已经装了** `商品A`。因此，在测试执行合并时，我的探针证明代码**准确地走进了专门用于合并商品的那个 `If` 分支代码块**——也就是去累加那个旧商品的购买数量 (`item.setQuantity(old + new)`)，这让系统免于愚蠢地走入 `Else` 并在数据库插入两条完全一样的相同的订单行。”

**不仅如此，我还走了一个“容错防护分支 (`Null Check`)”：**
> “同样是这个购物车服务，在调用另外一个 `getPopulatedItem()` 去拿购物车明细时，我故意传了一个包含已被商家偷偷下架/物理删除的商品的非法 ID。当时调试 `if (product == null)` 这个极冷门的判断条件时，”
> “这段代码终于走进了异常处理分支，完美拦截并安全返回，这确保了即使用户的车里装了已下架过时产品，整个商城的页面也不会白屏报出可怕的 `NullPointerException` (空指针异常)。”

“通过这些针对性的白盒覆盖侧试，我强行迫使购物车服务这段‘雷区’的代码覆盖率**向上拉升了近 30个百分点**，把几十行以前大家都忽视、但最容易出问题的判断分支全踩踏实了一遍。”
